## The split (9 Sep 2026) — what this project owns, and the one rule that keeps two projects safe
This project **owns** the Trainbot and everything around it: `elysium-bot.js`, `elysium-bot-arena.js`, `elysium-bot-table.js`, the `gen-*` trace tools, the cardfx pipeline (`cardfx-compile.js`, `cardfx-curated.json` → `elysium-cardfx.json` + `.js`, `test-cardfx.js`), the arena decks (`deck-*.json`, `rig-a1.json`), the bot suites (`test-bot-logic.js`, `test-bot-canary.js`, `diag-hb1-smoke.js` + `elysium-bot-diag.html`), the bot design canon and `START-HERE-BOTS.html`.

The sister project **Elysium** (main) owns the client (`elysium-vtes-bord.html` — including hotBridge, the hotseat-bot UI and HOT_BOT_DECKS), the server, the test harness, the client/server suites, `ELYSIUM-PROTOCOL.md`, ops and the main living docs.

**THE RULE: consume releases, never edit the other project's files.** Three files here are READ-ONLY copies of main-project releases, kept only because the arena spawns a real server and the bot speaks the protocol: `elysium-server.js` (srv-2.6.32), `ELYSIUM-PROTOCOL.md` (the contract) and `elysium-hotseat-bots-plan.md` (the client-side bridge architecture). Never patch them here — if a bot feature needs a wire verb, a client change or a server change, WRITE THE NEED in the journal + context, let the main project ship the contract first (or ship the bot first if the change is backward-compatible), and consume the new release in the NEXT session. Never both sides in one round. A release from here = a bumped `BOT_VERSION` + one entry in `elysium-bot-CHANGELOG.md` + the files the main project bundles (`elysium-bot.js`, `elysium-cardfx.json`, `elysium-cardfx.js`, `START-HERE-BOTS.html`).

One ingredient of the decision (a target, a score part) is not the decision: the first cut played the Haven on the rush chooser's target and the rusher then equipped a retainer. **And test a phase effect through the phase:** a hook a unit test calls directly proves the hook, not that the turn calls it (Arcane Library's influence lock had such a test and never fired in play; the probe reservation is set and reset two lines apart while its test sets it by hand).

**The window rule (v0.6.206):** a window opens in the SAME tick as the line it opens on — never an `await` between sending that line and `_askBlock`: at pace 0 a bot answers in ~50 ms, and an answer with no ask open is lost (the bleed total slept 150 ms there from v0.6.144 to v0.6.206 — two windows in three ran out their clock, and a bounce's new target's block was dropped). A guard about what the table has SEEN keys on the line the answer answers (`_openLine`), not on my whole queue (my board push follows a modifier's add line). After a smoke, `python3 ana-windows.py <serie>`: windows that ran out their clock and went through = 0; read every `stale-answer` row. And **count in the arena, weigh in a lab**: a decision the arena meets once a match is measured on the same table per arm (`lab-probe.js` + `ana-lab.py` is the pattern); the arena proves the knob fires and carries the audits.

**Knob hygiene (v0.6.162):** a decision knob (`combatMind`, `permFirst`, …) gates DECISIONS only. A rules correction (what a card or strike legally does, what a message means, a timing race) is never behind a knob — otherwise the documented rollback re-introduces the bug. When a release mixes the two, split them before shipping.

**The ledger gate (v0.6.163):** after any series, `python3 ana-ledger.py <serie>` — bleed pairing, combat opponent names, dealt vs taken, steal balance, creep. An effect that moves something between two bots and shows on only one side is a bug until explained (three of this week's bugs were exactly that shape). **v0.6.196: resolve an effect at its RULES moment, not when its line arrives** — the victim of a steal paid on the line, before its own strike was chosen, so its later dodge / combat ends could not stop it (the stealer undid its side correctly). The steal balance in totals hides this; count the precise symptom instead: blood lost in a round I ended or dodged. **And pair the rows before accepting an explanation for a total:** the steal totals had been explained as "capping" (the victim cannot lose more than it holds) — true, and it hid the stealer gaining the card's full number from an empty vampire in about one steal round in five (fixed in v0.6.196, `_stealAvail`). `ana-ledger.py` now prints `4 steal pairs`; after the fix every pair in `fix2` was equal, so a `STOLE > VICTIM LOST` row is a lead to chase (one known edge: a victim paying blood for its own strike in that round, after the stealer read its count). **v0.6.202: the bleed pairing runs both ways** — a bleed `through` that no seat took is `VANISHED`. Fixed in v0.6.203 (a bounce opens its new target's block step; a bot actor's It resolves lands an attempt it never took up; `through` is emitted at the resolution, with `final`): the gate is 0.

**The block gate (v0.6.170, Johan: base rules):** stealth and intercept are spent only when needed — the actor plays stealth only after a block attempt and only while intercept ≥ stealth; the blocker plays intercept only while stealth > intercept. Directed actions carry 0 stealth; the undirected +1 applies to the BASIC actions only (hunt, equip, employ, recruit, political, rescue own vampire, leave torpor) — an ACTION CARD is at 0 stealth unless it prints stealth, and its printed "+N stealth action" is the total (rulebook, Action cards; sweep pilot 25 Sep). cardfx `actStealth` is that printed total. **The event log (v0.6.176):** a new frozen line gets its event kind in `_evClassify` in the same release as its parser — never a parser alone. Phase A records only; when a reader moves to the log (phase B), the loose field it replaces is deleted in the same release.

**The hold gate (v0.6.198, Johan's principle agreed with main 12 Oct):** a Hold on stops EVERY clock that waits on a human and each starts again from the beginning on the release. A new wait on a human therefore needs four things beside its tempo kind: its arm function checks `_held()` and freezes (`_freezeWait`: timer, deadline, Turn-based reminder) instead of arming; `_holdFreeze` freezes it when a hold lands; `_holdThaw` re-arms it FRESH when `_holdBy` empties (every release path calls it: `_holdHook`, `step()`'s Release hold, `_releaseDeparted`); and if the bot sits inside it with nobody else to announce, `_holdAnnounce()`. A one-shot timer that waits on a human uses `_heldTimeout(fn, ms)`. An ANSWER still ends a wait at once; completion (everyone has spoken) is not a clock. The hold is the TABLE hold (`_holdBy`, the badge): a vote, a Yes or a No is an answer, never a release — only the flow phrases (No block, Block!, No reaction, It resolves, Pass; typed carry on / resume / it resolves) release. The ask's `pausedBy` and the poll's `paused` follow the table hold: a release by anyone ends every holder's pause (`_releasePauses`) — an independent review found that a pause outliving the release hung the poll (no clock, no button) and swallowed a target's Pass. Every frozen wait of mine says the hold once (`_holdAnnounce`), and a question asked under a hold must not promise a clock (`_waitTail`). Bots never operate the hold, so the arena never reaches any of it.

**The tempo gate (v0.6.194, Johan's design `spec-bot-tempo-2026-09-27.md`):** a wait on a HUMAN never reads `askSecs` / `phaseSecs` directly — it asks `_waitPlan(kind, who)` (kinds: block / react / pq / vote / phase / damage) and writes a `wait` row when it ends. A new wait on a human gets its kind in `_waitPlan`, its `t0`, its row, its Turn-based reminder text, and a `status()` / `step()` rung so the Bot button can end it — or it is a wait the tempo cannot see. Bot-vs-bot windows (the handshake's `_strikeWaitMs`, `_awaitOpp*`, a bot target's ask) never read the tempo (`mode: 'bots'`); a change there is a handshake change, not a tempo one. Adaptive's skip is RULES-strict: a question is skipped only when the human has no legal way to answer it (no ready minion; locked minions + empty hand; a reaction / "anything before" with an empty hand) — never on a prediction of what they would do; the strike and the press are always asked. And a shortened wait that was also somebody's only window to answer (the human's press to end after my press) becomes an asked, tempo-governed step (`_phaseStep(5, 'reply')`), never just a shorter silence.

**Lines are the contract, fields are the accelerator (main, 23 Sep):** every combat decision taken from a tally field must have a line fallback (range from `maneuvers to` / `sets range to`, press from `presses to`, strikes from the strike lines, damage from `takes N (…)`); prefer a HUMAN's field when it disagrees with the last line; never require the field. `combatPhases` must not be built on `ph`.
